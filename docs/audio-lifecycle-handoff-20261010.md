# Claudeへ渡すメモ：画面を閉じた後に音が残る問題

2026-10-10。ユーザーが「ブラウザを落としてもBGMが鳴る」と報告。共通ルールの候補として整理する。この文書自体で全プロジェクトの憲法を変更したり、Claudeへ自動送信したりはしていない。

## 確認できたこと

EmmichyはWeb Audioの音源と1.8秒ごとのタイマーでBGMを作っていた。音OFFでは消音していたが、画面の非表示・ページ離脱で音を停止／解放する処理がなかった。バックグラウンドの生きたページで鳴り続ける経路があった。

調査時、Codex内にはこちらが作ったローカル試遊タブが1枚残っていた。操作で音が始まるため、この試遊タブも音源になり得た。タブは閉じた。ただし、音声出力の発生元を実測できておらず、これが報告された音の原因だったとは断定しない。

ブラウザの窓を閉じたのか、内蔵ブラウザの表示欄を閉じたのか、最小化なのかは未確定。プロセスが完全終了した後にも同じページの音が鳴り続けた、とは確認していない。

## Emmichyでの修正

- `visibilitychange`で非表示、または`pagehide`で離脱したら即時に消音する。
- 再生タイマーを解除し、予約済み音源も停止・切断する。AudioContextを閉じて音声資源を解放する。
- ONという選択は保持するが、画面に戻っただけでは再生しない。次のプレイヤー操作で一度だけ再開する。OFFを選んでいたら再開しない。
- 開始処理の待機中に画面を離れても、古い開始処理が戻って音を復活させない。
- 普通の画面確認は試遊タブ内で音OFFにして行い、完了後に作業者が作ったタブを閉じる。

## 共通ルールとして採用する案

音を出すアプリは「画面の終了・非表示」と「音の終了」を明示的に結びつける。背景再生をユーザーが希望する音楽プレイヤー等は別仕様とし、ゲームや試遊ページは非表示で止める。

停止処理は繰り返し呼んでも安全にし、出力の消音、予約済み音源、タイマー、音声資源、待機中の開始処理をまとめて管理する。非同期処理が停止後に再生を復活させないこと、OFFを復帰が上書きしないことを検証する。

終了イベント一つに頼らない。埋め込みブラウザ／WebViewの表示欄を閉じてもページが生きている構成では、ホスト側の非表示・破棄通知でも明示的に停止する必要がある。ページ側だけで、そのホストが非表示を通知することまでは保証できない。

エージェントが開いた試遊ページは作業終了時に閉じる。画面確認だけの操作で音を出し続けない。ユーザーが開いたタブやブラウザ全体を勝手に閉じたり、無関係なプロセスを終了したりしない。

## 検証と残る確認

Emmichyの自動テストは、非表示・離脱時の出力ゼロ、タイマー消滅、予約音源の停止／切断、Contextのclose、復帰時の自動再生なし、OFF維持、開始と終了の競合を確認した。これは模擬AudioContextによる処理の検証。

実際のスピーカーで無音になったか、ユーザーが行った「閉じる」操作でホストがどの通知を送ったかは未検証。実機ではタブ切替・最小化・離脱・戻る・タブ終了・内蔵表示欄終了・複数タブを個別に確認し、鳴っているタブを特定して記録する。再生開始の連打／直後の終了も含める。

## 技術的根拠

背景タブの音が自動で止まることは前提にできない。MDNには非表示で音声を止める例があり、再生中の音声タブがタイマー抑制の例外になる説明もある。[Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

`pagehide`は、特にモバイルで必ず発火するイベントではない。非表示の通知も使う。[pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event)

`AudioContext.close()`は音声処理を停止しシステムの音声資源を解放する。ノードへの参照の整理も必要。[AudioContext.close](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/close)
