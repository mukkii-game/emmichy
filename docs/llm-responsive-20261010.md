# LLMを使いながら待たせすぎない

前回の仮想プレイヤー19送信は明示的なオフライン試遊。公開版のLLM選択率を測った結果ではなかった。ユーザーの追加指示は「1プレイで最低1回、可能ならもっと使う。待ち時間は別の反応で埋める」。

従来は最初の適切なターンでLLMを優先しても、その後の用意済み返答は多くがruleOnlyになっていた。最終指示は「良いLLMの続きは優先し、半々の割当で強制終了しない」。採用数は観察用に記録するが選択の割当には使わない。現在は通常の感想・日常・ファン話・褒め言葉などで、用意済み返答を通信失敗時の候補として残しながら毎ターンLLMを試す。最初の実際に採用したLLM本文まで優先し、全置換した本文をLLM採用と偽って数えない。固定出身、初期挨拶、別れ、計算、記憶回答、話題の拒否と性的な話の転換は即答を優先。最初の成功後の閉じた本人設定も即答を維持する。

名前や好意への短い反応は従来通り約0.75秒。通信中の約2秒で短い相づち、約5秒で現在の話に合う用意済み台詞の短い最初の部分を話す。どれも正式な履歴に残し、新しい通信は増やさない。返事が来たら予定中の相づちは取消す。本文が遅すぎる時は8秒で通信を打ち切り、関連する用意済み返答へ進む。入力演出や文字表示の時間はこの8秒の通信予算とは別。入力済みの下書きには続きを差し込まない。

中継はこのゲームだけ各providerの待ちを5秒から2.5秒に短縮し、次のproviderへ早めに進む。Gemini→Groq→Workers AIの順序・出力上限・他ゲームの設定は維持。情報確認の1.6秒は別で、全chainが遅い場合は画面側が8秒で切り替える。通信失敗の60秒休止、429時のそのプレイ内停止は維持する。回線切断・上限・出力の品質不良時にも、少なくとも1回の実回答成功を保証したとは言わない。

変更前の実通信確認：「今日は散歩で小さいパン屋を見つけたよ」→Groq、HTTP200、6,032ms。実appの採用数ai=1。「小さなパン屋、見つけたんだね！」から香り・本人のシナモンロールの好みへつながった。`live-llm-current-20261010.json`。

それ以前の試遊アダプターの文字コード失敗、既定User-AgentでのHTTP403はログに残す。ハーネスを修正し、公開サイトのOriginと明示User-Agentで通信した。これらをLLM選択の少なさやproviderの生成失敗の証拠にしない。実画面・音・本物のIMEの評価ではなく、実appと公開中継の試遊である。仮想clockによる発言時刻と、実通信のwallMsを区別する。

検証：最初の採用に続く通常バンクのターンでもLLMを呼んで採用する実appテスト、8秒のAbortSignalと通信中断時のfallback、制御回答・オフライン・429、下書き・話題・終了の既存回帰。追加サブエージェントは使わない。追加実通信は停止。

追加の実app試遊（live-llm-mixed-20261010.json）は3通信: Groq/HTTP200/3653ms、HTTP502/5401ms、HTTP502/5345ms。1本文を採用し、失敗時の話題に合う短い待ち台詞とDBへの移行を確認。502のprovider側原因は未特定。仮のバランス調整中のログであり、最終の比率なし選択の実測とは称さない。

2通信予定が3回目まで進んだ原因: 相づち保存や5秒の自動保存がsessionをコピーし、保留中のrequestChatが更新した通信成否・休止時刻を失っていた。保存と復帰を同じsessionへの更新に直し、実appの遅い通信中に2秒／5秒の待ち台詞と自動保存を行ってから429を返す回帰を追加。通信失敗の情報が残り、次の発言で再通信しないことを確認した。最終修正後の実通信は追加せず、回帰と公開配信一致で確認する。
