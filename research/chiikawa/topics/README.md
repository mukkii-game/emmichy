# SNS・ニュースから会話の話題を集める

目的：原作に詳しいえみちぃが、ファンがいま気にしている場面・グッズ・食べ物・イベントを知り、相手と具体的な感想を交わせるようにする。情報を集めるだけでなく「なぜこの話を今の相手にするか」まで持つ。

## 調べ方

X（Twitter）、Threads、Instagram、Webニュースを対象にする。公式発表・原作投稿を起点に関連する公開投稿や記事を探す。ちいかわ中心だが、会話に接点がある日本・アニメ・漫画・ゲームの話題も扱える。

まず直近7日、少なければ30日、過去の話題はその当時の反響として調べる。投稿本文を読めたか、反応数を見られたかを別々に記録する。検索要約や転載だけを元投稿の確認にしない。見えないものは取得不可／不明。取得不可でも公式情報で裏付けられる候補は保存できる。

「話題」の判定：

- measured：元投稿の反応数を取得し、観測日時・比較対象も記録した。件数一つだけで大流行を断言しない。
- corroborated：独立した複数の反響資料を本文確認した。同じプレスリリースの転載は一つと数える。
- media-reported：記事が反響を報じているが、元投稿の規模は直接確認できていない。「記事で取り上げられていた」まで。
- unverified：新着・おすすめ・公式告知だけ。話題性は未確認。新しい事実としては使える。

原作の事実は一次資料を優先。SNSの感想や考察は、その人／一部ファンの見方として持ち、公式設定やファン全員の総意にしない。商品名だけで原作場面を証明しない。推測・丸ごと転載・歌詞収集・非公開投稿の収集はしない。

## 保存形式と分担

このフォルダへUTF-8 JSONを保存する。担当ごとにgemini-topics.json／claude-topics.jsonなど別ファイルに書く。既存の原作CSVへSNS反響を混ぜず、相手のファイルを変更しない。snapshot-20261013.jsonが形式見本。Codexが出典と矛盾を検査して採用を決める。

各topicに固定キー：id、subjectIds、tags、publishedAt、checkedAt、fact、factSources、attention、conversation、spoiler、temporal、reviewStatus。各sourceはurl／publisher／kind／bodyChecked。attentionはstatus／sources／metrics／limitations。metricsが見えなければ空配列とし、0反応とは解釈しない。conversationはconnectFrom／personalAngle／question／avoidを持ち、感想案は創作と明記する。

商品・イベントは期間を保持。予約終了後に「予約できる」、未開催を「行ってきた」と言わせない。在庫・運営・反響は原則7日以内に再確認し、期限が過ぎれば現在形の案内を止める。過去の出来事として扱う場合も当時の日付を残す。

最初は各担当5〜10件で十分。公式根拠、関係する人物・場面、反響の確認範囲、会話接点の揃った候補を優先し、件数のために不明な流行を足さない。完了時に担当・件数・確認した媒体・取得不可の媒体・残る疑問を自分の成果ファイルへ記録する。新API契約、無期限の自動調査、ゲームへ自動投入はしない。

## 会話へ使う条件

相手の質問に答えてから、同じキャラ・場面の新しい角度として使う。「ハチワレの姿が変わる話→関連マスコット→自分ならどの姿を飾るか」など。一度出したtopic IDと感想の角度を記憶し、同じ紹介を反復しない。訂正・不満・回答待ちの質問の途中に挟まない。えみちぃの訪問・購入・鑑賞経験は本人設定にない限り作らない。

更新は会話の外で少数を検証し、関連する数件だけLLMの根拠へ渡す。プレイ中にSNSを毎回検索して待たせない。自動定期更新は未実装、今回の指示だけで定期ジョブを作らない。

## 2026-10-13の初回確認

公式商品本文、パーク個別告知、ニュース記事を確認し2候補を保存。ニュースが「話題」と呼んだ例はあるが、測定済みの人気投稿は0件。公式商品のX元投稿は403、Threads／Instagramは検索で本文・反応数を得られなかった。検索やプロフィール取得の失敗は、投稿やアカウントの不存在の証拠ではない。SNS全媒体の調査完了・ゲームへの採用完了とは報告しない。
